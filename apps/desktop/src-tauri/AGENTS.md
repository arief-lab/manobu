# apps/desktop/src-tauri

## Purpose

- Tauri v2 desktop shell for manobu. Compiles a Rust binary that loads the SPA from `apps/desktop/dist/`, spawns the `server` sidecar (Hono backend on `127.0.0.1:4317`), and (when present) registers the `jlpt-mcp` stdio sidecar for the ACP agent.

## Ownership

- Project contributors.

## Local Contracts

- Bundling
  - `tauri.conf.json` — `productName=manobu`, `identifier=gg.manobu.app`, `app.withGlobalTauri=true` (TASK-154: injects `window.__TAURI__` into the packaged webview; every frontend Tauri detector tests `"__TAURI__" in window` — `tts-init.ts:16`, `speech/src/tts.ts:5`, `queue.ts:70`, `cron.ts:8` — so without this the built app silently runs every gated path in web mode, e.g. no voice offer in the exam), window `1440×900` (min `900×600`, max `1600`), centered, resizable; `bundle.targets=["deb","appimage","rpm"]` (updater/single-instance/window-state plugins out-of-scope for v1, document if needed); `app.security.csp` strict `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: asset: https://asset.localhost; connect-src 'self' ipc: http://ipc.localhost tauri://localhost http://tauri.localhost http://localhost:4317; font-src 'self' data:` (was `null`; `http://tauri.localhost` is the WebView2 origin a Windows package serves from, listed beside the WebKitGTK `tauri://localhost` because an origin a platform never sends is inert); `externalBin` resolves to compiled `apps/server/dist/server` and `crates/jlpt-mcp/dist/jlpt-mcp`; `bundle.resources` ships `assistant/` (persona markdown) plus every file and directory the sidecar opens under `resolveDataDir()`: the five `packages/japanese/data/n{1..5}.json` bands, `kanji.json`, `verbs-n5.json`, and the `grammar/`, `reading/` and `kanjivg/` directories. **The invariant is "what the server opens" versus "what the bundle carries", and `apps/server/test/bundle-resources.test.ts` holds it** (TASK-178): `data/reading` was missing from this list while `n5.json` was present, so `resolveDataDir()` resolved happily, `readJson` returned `null` for every store, and a real paper printed 43/91 items at N5 with the blame aimed at the blueprint. Adding a read site in `apps/server` without adding its resource here fails that test; `tauri build` cannot see the omission itself.
  - `tauri.linux.conf.json` maps `resources/vaporetto` → `resources/vaporetto` (the sqlite-vaporetto `.so` and the BCCWJ+UniDic model, 39 MB). This leg is NOT under `resolveDataDir()`; `packages/db/src/vaporetto.ts` walks for `<dir>/resources/vaporetto/ext` from the exe dir and the cwd, and `lib.rs` sets the cwd to the resource dir, which is why the destination keeps the `resources/` prefix. Absent it every packaged boot runs unicode61, `exam-mask.ts` reports each derived candidate unmaskable, and a learner's FIRST N5 real paper comes up 15-16 小問 short blaming `contentExhausted` (measured on the delivered AppImage: 76/91 with 文脈規定 and 文の組み立て at zero; the rebuilt one boots `tokenizer=vaporetto` and prints 91/91). Guarded by the same test's `bundle resources carry the tokenizer assets` block, which also pins the PLACEMENT: the leg must be in the linux config and must NOT be in the base one, because a platform override only ever adds to the base, so declaring it in `tauri.conf.json` would push 39 MB of Linux-only bytes into the NSIS installer, where no `.dll` exists to load them. No Windows equivalent ships: `sqlite_vaporetto.dll` has never been cross-built, so the NSIS bundle keeps the same hole until that happens (then it belongs in `tauri.win-x64.conf.json`).
  - **Windows packages are a separate config, merged over the base one** (TASK-177): `tauri.win-x64.conf.json` sets `bundle.targets=["nsis"]`, adds the `@libsql/win32-x64-msvc` resource leg and `bundle.windows.webviewInstallMode={type:"offlineInstaller",silent:true}`; `--config` deep-merges objects, so the base resources (including the linux `@libsql` leg, which is dead weight there) survive into the Windows bundle (proven from the generated `target/<triple>/release/nsis/x64/installer.nsi`, not assumed). A merge can only add: what must NOT ride along has to live in a `tauri.{platform}.conf.json` the other build never reads, which is where the vaporetto leg sits. That mode is what makes the installer self-contained: the ~205 MB `MicrosoftEdgeWebView2RuntimeInstallerX64.exe` is embedded (`WEBVIEW2INSTALLERPATH` + `WEBVIEW2INSTALLERARGS "/silent"` in the generated NSI) and run only when the EdgeUpdate registry probe finds no runtime, so a machine that already has WebView2 pays nothing and a machine without it needs no internet at install. With `downloadBootstrapper` (Tauri's default) the installer is 71 MB and `NSISdl::download` from `go.microsoft.com` runs `Abort` if that fetch fails; embedded it is 275 MB and cannot fail that way. `install_mode` stays the default `currentUser` (per-user, `RequestExecutionLevel user`, no UAC). The bundles install the sidecars beside the exe under their **plain** names (`server[.exe]`, `jlpt-mcp[.exe]`): the `-<triple>` suffix exists only in the staging dir `dist/`, and the bundler renames it away, so any runtime lookup must use `name + std::env::consts::EXE_SUFFIX`, never the triple.
  - `capabilities/default.json` — `core:default` + `shell:allow-open` + `shell:allow-execute` scoped to `binaries/server` sidecar with `args=false`, `env` scoped to `[BUN_PORT, CORS_ORIGIN, NODE_ENV, DATABASE_URL, MANOBU_ASSISTANT_DIR, ACP_MCP_SERVERS, MANOBU_PARENT_PID, MANOBU_CACHE_DIR, MANOBU_LOG_DIR]` (was `env:true` wildcard; the last three are the TASK-153 ownership contract). `speech::*`/`fsrs::*` custom invokes are covered by `core:default` (no extra capability needed for v1). Adding a new sidecar or extending shell access requires a new entry here.
  - `build.rs` — cross-MSVC fix: `lld-link` on a case-sensitive host opens `/DEFAULTLIB` names verbatim, and `onnxruntime.lib` (the sherpa prebuilt) asks for `PathCch.lib` while the cargo-xwin SDK ships `pathcch.lib`, so the build script generates a correctly-cased alias directory from the `-Lnative` entries of `CARGO_TARGET_<TRIPLE>_RUSTFLAGS` and adds it to the link search path. A new mis-cased import library is one entry in `IMPORT_LIB_CASE_ALIASES`; native `link.exe` folds case and never needs any of this (`link_import_lib_aliases` no-ops on a Windows host).
- Sidecar lifecycle (`src/lib.rs`)
  - Spawns the `server` sidecar on boot with `BUN_PORT=4317`, `CORS_ORIGIN=tauri://localhost,http://tauri.localhost,http://localhost:4317`, `NODE_ENV=production`, `DATABASE_URL=file:<app_data_dir>/manobu.db` via `app_data_dir().join("manobu.db")` (was `format!("file:{}/manobu.db", display)`), plus the TASK-153 ownership contract: `MANOBU_PARENT_PID=<tauri pid>` (sidecar self-exits when this pid vanishes — `apps/server/src/parent-watchdog.ts`), `MANOBU_CACHE_DIR=<app_cache_dir>` and `MANOBU_LOG_DIR=<app_log_dir>` (both `create_dir_all`ed in setup; the sidecar never derives paths from cwd — `GET /api/system/info` on the server reports them).
  - **Debug builds append the dev origin.** `cfg!(debug_assertions)` adds `build.devUrl`'s origin (e.g. `http://localhost:3001`) to `CORS_ORIGIN` in `lib.rs`. Without it the whole RPC surface is CORS-rejected under `tauri dev`: the sidecar is up and healthy, yet `useSenseiStatus` gets no response and the setup rail reads "backend unreachable". The server's own dev-localhost fallback (`apps/server/src/index.ts`, `DEV_LOCALHOST`) cannot cover this because the shell pins `NODE_ENV=production` for both profiles. Release keeps the strict two-origin list, so shipping behaviour is unchanged.
  - Resolves `MANOBU_ASSISTANT_DIR` from `bundle.resources` first, falling back to `<exe-parent>/assistant` (dev sync via `apps/desktop/scripts/sidecar-dev.sh`).
  - Sets `ACP_MCP_SERVERS` with precedence `env literal → config/mcp-servers.json enabled entries → bundled jlpt-mcp` (`mcp::resolve_acp_mcp_servers`, whose third arm is handed `bundled_jlpt_mcp_path(current_exe())` = `<exe parent>/jlpt-mcp<EXE_SUFFIX>`, the name the bundle actually ships); user override still wins. Any stdio target containing whitespace is wrapped in double quotes by `mcp::quote_stdio_target` before it enters the literal, because a Windows install path (`C:\Program Files\...`) would otherwise be whitespace-split into a truncated command by `packages/acp` (TASK-177). Catalog managed via `McpCatalogState` (`src/mcp.rs`). NOTE (TASK-24.1): Tauri only EXPORTS the env var — the ACP agent (opencode) spawns the jlpt-mcp process per `session/new`, so Tauri cannot warm the agent's predictor instance (a `lib.rs`-side warm call would load a throwaway copy). The warm instead lives inside jlpt-mcp itself (`main()` background thread, `tokenize::warm()`), keeping boot-phase warm semantics without touching the readiness poll. Smoke: `apps/desktop/scripts/sidecar-warmup-smoke.sh`.
  - **Exit teardown is platform-split** (`shutdown_sidecar`, `src/lib.rs`). Unix: SIGTERM the sidecar (`libc::kill`, `child.pid()`) and wait up to `SIDECAR_SHUTDOWN_TIMEOUT` (2s, polling `/proc/<pid>`) so the server's own teardown can dispose every ACP session and reap its detached agent process groups (TASK-102 registry + TASK-153 AC#1: a bare `child.kill()` is SIGKILL and skipped all of that); `child.kill()` only escalates when the grace window expires. Windows: there is no SIGTERM to send and `tauri_plugin_shell::process::CommandChild` exposes no `try_wait`, so the parent cannot poll the child at all; `libc` is a `cfg(unix)` dependency and the arm deliberately hands the sidecar over to its own `MANOBU_PARENT_PID` watchdog (`apps/server/src/parent-watchdog.ts`, signal-0 poll every 2s) and logs that it did. Calling `kill()` here would be a SIGKILL-equivalent and would restore exactly the orphaning TASK-153 removed. `libc::kill` and the `/proc` poll are the only unix-only code in the crate.
  - Polls `http://127.0.0.1:4317/` HTTP 200 health via `ureq::get` (was raw `TcpStream` `GET /`), spawned off the main thread via `std::thread::spawn` (was blocking `thread::sleep` poll on main thread up to 30s). Logs and opens window immediately; `/ai` calls fail until ready. On timeout it names the port holder with `sh -c "ss -tlnp"` (TASK-48); that diagnostic is guarded by `if let Ok`, so a Windows build simply loses the extra log line and keeps the poll itself.
  - **On success the poll emits `sidecar:ready`** (`SIDECAR_READY_EVENT`, `Emitter` on a cloned `AppHandle`). The window mounts while the poll is still waiting and the sidecar applies DB migrations before it listens (spawn → `[ai] listening` measured 15s), so the webview's first RPCs can fail against a closed port; `src/lib/sidecar-ready.ts` re-runs the status probe on this event. Nothing is emitted on timeout — a genuinely absent backend stays reported by the rail's own `re-check` rather than endless retries. `core:default` already covers `core:event:default`, so no capability change.
- Linux + Hyprland/wlroots + NVIDIA workaround (`src/main.rs`)
  - Sets `WEBKIT_DISABLE_DMABUF_RENDERER=1` before WebKitGTK loads to dodge the GBM-buffer crash on NVIDIA proprietary + Wayland. Skip when `WEBKIT_DISABLE_DMABUF_RENDERER` is already set. Document any override or removal in the commit message. `Cargo.toml` `rust-version = "1.85"` (was 1.77.2); `unsafe { std::env::set_var }` required since Rust 1.66, so 1.85 is correct.
- Commands (`#[tauri::command]` in `src/`)
  - `speech::*` — TTS / STT / VAD / model management via `@manobu/speech` (sherpa-onnx, on-device). TTS (`tts.rs`, TASK-154): `speech_init_tts` builds a real `TtsEngine` (Sherpa `OfflineTts` + Supertonic 3 int8 JA, 7-file stage set from `models::SUPERTONIC_FILES`, `num_threads=2`) and stores it as `Arc<OfflineTts>`; `speech_tts` generates in `spawn_blocking` with `GenerationConfig { extra lang="ja", num_steps=8, sid, speed }`, encodes PCM16 mono at the engine rate (44.1kHz) into a 44-byte-header WAV, and returns `not_initialized` when no engine is loaded — no silent-wav stub, the frontend treats that error as "no voice". `models.rs` is Supertonic-aware: kind-aware validation, `model_ready`, and the absent-dir report all branch on a directory name containing `supertonic` (`is_supertonic_dir`). STT (`speech_stt_file`) builds a real `OfflineRecognizer` (SenseVoice, `ja`, ITN) at init when the model dir validates (`model[.int8].onnx` + `tokens.txt`), decodes inside `spawn_blocking` via `Wave::read`, and falls back to a filename-echo stub when files are absent; `speech_write_temp_wav` wraps mic PCM16 bytes in a 44-byte WAV header under `app_data_dir/speech/tmp/` so no extra `fs` capability is needed; the client-supplied `stem` goes through `sanitize_stem` first (ASCII alnum plus `. _ -`, capped at 64 chars, leading dots stripped, `rec` when nothing survives) because `* ? " < > |` are illegal filename characters on Windows and `/` or `..\` would traverse out of the tmp dir. Streaming STT (TASK-21.5): `stt.rs` also holds `OnlineSttEngine` (Zipformer `OnlineRecognizer`, greedy_search, endpoint rule1 0.5s / rule2 0.75s utb, `Arc` so decode tasks never hold SpeechState locks) in `SpeechState.stt_online` plus a `SpeechState.stt_streams: Mutex<HashMap<String, StreamSession>>` session map; commands `speech_init_stt_stream` / `speech_stt_stream_is_ready` / `speech_stt_stream_create` / `speech_stt_stream_accept` (decode-while-ready per chunk, endpoint → `{final:true, text}` + `reset` so the session continues) / `speech_stt_stream_finish` (0.3s tail pad + `input_finished` before the final drain; session dropped) / `speech_stt_stream_close`. Without a linked recognizer the engine is stub-only and `accept` echoes `[stub stream] N`; with dummy ONNX payloads sherpa throws foreign C++ exceptions, so stub detection must happen *before* `create` (missing tokens.txt) — corrupt models are `speech_validate_model`'s job. Testable cores `init_stt_stream_state` / `stt_stream_create_in` / `stt_stream_close_in` take `&SpeechState` (no AppHandle) for unit tests.
  - `cron::*` — `cron_list/upsert/remove/history/clear_history/run_now/due_jobs/keep_awake_armed/report_result` (Tier B); `mcp::*` — `mcp_catalog_list/upsert/remove` (Tier C `config/mcp-servers.json`).
  - `fsrs::*` — FSRS scheduler math (parameters, preview, next states, optimize, snooze, vacation, leech gate, optimal, reschedule).

## Verification

- `bun run desktop:dev` — Tauri dev (triggers `bun run dev & bun run sidecar:dev` then opens the window).
- `bun run desktop:build` — produces `.deb` + `.AppImage` + `.rpm` bundles (was `.deb` only; `beforeBuildCommand` runs `../scripts/sidecar-stage.sh`, which compiles and stages both sidecars at the `externalBin`-named `dist/` paths and guards their freshness — a stale or missing sidecar fails the build instead of packaging silently (TASK-151). The script carries `NO_STRIP=true`: linuxdeploy's bundled 2024 strip cannot read the `.relr.dyn` sections Arch-family toolchains emit, and its strip failure kills the AppImage target (linuxdeploy/linuxdeploy#272). `tauri-plugin-updater`/`single-instance`/`window-state` out-of-scope for v1).
- `bun run desktop:build:windows` — cross-builds the `x86_64-pc-windows-msvc` NSIS installer from this Linux host (`--runner cargo-xwin --target x86_64-pc-windows-msvc --bundles nsis --config src-tauri/tauri.win-x64.conf.json`). Needs `rustup target add x86_64-pc-windows-msvc`, `cargo install cargo-xwin`, `lld-link`/`llvm-rc` and a `makensis` **on `PATH`** (the bundler runs `Command::new("makensis")` on a non-Windows host; its error string says `makensis.exe` regardless, and the NSIS zip it would otherwise download is `cfg(target_os = "windows")` only, so no distro package means no installer; Arch has no `nsis` in the sync DB, it is an AUR package). `offlineInstaller` adds one more prerequisite: the build host must reach Microsoft's CDN the first time, which caches `MicrosoftEdgeWebView2RuntimeInstallerX64.exe` under `~/.cache/tauri/<arch>/<guid>/` for every later run. Proven end to end on this host: the exe links, the sidecars stage, makensis loads the Windows PE plugin `nsis_tauri_utils.dll` (the one Linux-side worry; only `warning 5202 -OUTPUTCHARSET is disabled for non Win32 platforms` comes out), and `bundle/nsis/manobu_0.1.0_x64-setup.exe` is produced. What no Linux check can reach is the archive content (no `7z`, `bsdtar` cannot read NSIS, and the file table is compressed) and everything about running it: install, WebView2, sidecar boot, libsql, sherpa voice. `XWIN_CACHE_DIR` moves the MSVC CRT/SDK cache.
- `cargo check --manifest-path apps/desktop/src-tauri/Cargo.toml` for Rust-only changes (must pass with `rust-version 1.85`).
- `cargo xwin check --release --target x86_64-pc-windows-msvc --manifest-path apps/desktop/src-tauri/Cargo.toml` (or the same `build`) — the only static proof that the `#[cfg(windows)]` arms compile; a Linux `cargo check` never type-checks them.
- `cargo fmt --check --manifest-path apps/desktop/src-tauri/Cargo.toml` — the crate is rustfmt-clean and `.husky/pre-commit` gates it whenever a `.rs` file under it is staged (TASK-98, same contract as `crates/jlpt-mcp`). Format with `cargo fmt --manifest-path apps/desktop/src-tauri/Cargo.toml`; there is no local `rustfmt.toml`, the crate is one default rustfmt run, and hand-formatting or suppression is not the contract.
- `cargo test --manifest-path apps/desktop/src-tauri/Cargo.toml` — 59 unit tests in the `app_lib` target (`cron.rs`, `mcp.rs`, `speech/models.rs`, `speech/stt.rs`, `speech/tts.rs`, `speech/vad.rs`, plus the bundled-sidecar-name lookup in `lib.rs`); the model-dependent STT/VAD paths degrade to stubs when the weights are absent and TTS hard-errors on a missing/incomplete model dir, so a green run proves the stub/error contracts, not the sherpa paths.
