## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Every generated exam paper draws its vocabulary from SIXTEEN hardcoded Japanese nouns. This is the largest content defect in the exam pipeline and it shipped unnoticed inside a task whose own acceptance criteria were all met.

EVIDENCE. apps/server/src/services/exam-service.ts:138-165 defines interface LocalCatalogEntry (answer, three hand-picked distractors, id) and LOCAL_CATALOG as 16 literals: 学校 先生 電車 本 友達 家族 水 朝 夜 駅 店 家 時間 日本語 音楽 天気. catalogOffsetFor (:424) hashes examId:seed:section:itemType into a starting offset and appendItemTypeCandidates (:440) walks LOCAL_CATALOG[(offset + index) % 16] to fill the allocation. So a paper is a rotation of those 16 nouns, and the same rotation feeds EVERY item type: a conjugation item and a particle item are both built from 学校/先生/電車. The itemType drives allocation and validation but not content, which is why seeded papers at N1, N2 and N3 all surfaced the same handful of words.

Meanwhile the corpus the repo already ships is never read by the exam path. That is where this task goes to get its candidates, and the amount of it is now measured (below).

WHY IT MATTERS BEYOND TEDIUM. The anchoring guarantee is the anti-hallucination design (doc-16 §2: anchors is non-empty by construction; doc-14 §4: the agent supplies anchors, the assembler decides everything else). Today the anchors are digests of synthetic ids (vocab:N5:<digest> of the literal catalog), so anchor-missing and anchor-level are being checked against a 16-word list and mean nothing for a real corpus. A learner can also take two papers and see the same words.

THIS SHIPPED INSIDE TASK-126, WHICH MET ITS OWN CRITERIA. Its ACs asked for a request assembler, a validator and an exam state machine, and it delivered all three - the defect is that the candidate list handed to the assembler was never specified to come from the corpus, so nothing tested for it. The lesson belongs with this task: a pipeline task should assert where its inputs come from, not only what it does with them.

THE ORDER THIS IMPLIES. This is deterministic work and the model is not needed for it. Model-authored vocabulary (doc-14 §4's "anchors plus writing intent") is a later, separate decision, and it is worth making only AFTER the picker reads the real corpus - otherwise the model would be choosing from the same 16 words. The model does have a real role afterwards: stimulus prose and distractor sets that corpus entries cannot supply. Start with the grammar sections, which need no model at all (see the note below).

MEASURED SUPPLY (2026-09-26; do not re-derive, these are the planning numbers). JLPT-classified anchors: vocabulary 8,505 total (N5 700, N4 649, N3 1,835, N2 1,846, N1 3,475); grammar points 595 (N5 77, N4 89, N3 130, N2 149, N1 150); kanji 2,211 classified of 13,108 rows (N5 79, N4 166, N3 367, N2 367, N1 1,232 - the other 10,897 rows carry no jlpt_waller and cannot be level-assigned); plus a level-filtered subset of the 42 MB Tatoeba/Tanaka sentence corpus the crate embeds. That is 856 anchors at N5 and 4,857 at N1, so a 30-item paper with no repeated anchor is covered at every level, with room for a second and third pass over the same anchors.

THE SEAM ALREADY EXISTS - DO NOT REBUILD IT. crates/jlpt-mcp/src/main.rs:272 exposes drill_candidates(level, source, seed, limit), and its own tool contract is already the division of labour this task needs: "deterministic, corpus-backed source candidates for the shared item engine. The result contains canonical anchors and raw source entries only; it never contains prompts, options or answer keys." All four DrillCandidateSource variants are implemented - Vocab, Grammar and Kanji in engine.rs:423-460, Sentence at engine.rs:462-470 filtering corpus.all_sentences by sentence_level. Ranking is stable_hash(seed + anchor) with a seen-set dedup and a 50 cap, so it is already seedable, already deduplicated and already emits canonical anchors. So the mechanical half of this task is "consume the existing source layer instead of walking LOCAL_CATALOG", not "read 8,505 JSON entries and rank them", and the earlier estimate of one to two weeks was pessimistic about the plumbing and optimistic about the content. What the tool deliberately does NOT do is decide anything: it returns the raw entry with every sense still attached. Sense selection and distractor construction are this task's real work. One caveat to widen deliberately rather than by accident: DrillCandidate.anchors is built as vec![anchor], a single element, so an item that needs two anchors (a particle item that also tests a word) needs that widened on purpose.

GRAMMAR ENTRIES CARRY THEIR OWN AUTHORING MATERIAL. Every grammar point ships formation, formation_notes, meaning_detailed and examples alongside the pattern. A grammar item can therefore be authored from the corpus entry alone with no model call, which makes the grammar sections the cheapest honest items in a paper and the right place to prove the pipeline end to end before spending anything on prose generation.

- [ ] #1 The candidate catalog comes from the shipped corpus (packages/japanese/data/n1.json..n5.json), so anchors are real corpus ids and the anchor-missing / anchor-level checks mean what doc-16 §2 says. A test resolves at least one assembled anchor through the real corpus view and would fail if the catalog regressed to literals.
- [ ] #2 Each item type draws from a source that can actually support it: conjugation from verb entries, particle and grammar-form from grammar points, kanji-reading from kanji, listening from sentences. Today every type draws the same nouns. A test asserts a particle item anchors a grammar id rather than a vocabulary id.
- [ ] #3 Distractors are same-part-of-speech, same-form-class corpus surfaces per doc-14 §4, not hand-picked triples. The POS is available: every entry carries partOfSpeech.
- [ ] #4 A paper at one level draws a non-trivial number of distinct vocabulary items and does not repeat a word across items, asserted as a distribution over an assembled paper rather than one hand-picked item. A repeat is allowed only with a stated reason (a legitimately polysemous or inflected form).
- [ ] #5 doc-16 §2 and doc-14 §4 are corrected or satisfied: either the anchors are corpus ids, or the docs stop claiming the exam path is corpus-anchored. Whichever way it lands, docs and code agree.
- [x] #6 There is a second anchor namespace in the tree and this task must not invent a third. crates/jlpt-mcp/src/engine.rs::drill_candidates already mints canonical anchors - vocab:{level}:{word}:{reading}, grammar:{id}, kanji:{character}, sentence:{id} - while exam-service.ts mints vocab:N5:{digest}. doc-16 §2 resolves anchors through a corpus view, and a digest is not resolvable there, so the exam adopts the format the source layer already emits (or that format is lifted into @manobu/api-contract and both sides share it). A test asserts an assembled anchor resolves through the corpus view BY STRING rather than by array position, so the namespaces cannot drift apart again unnoticed.
- [x] #7 SENSE SELECTION, WITH THE REAL NUMBERS (the earlier draft of this AC was wrong: `meaning` is a single semicolon-separated STRING, not a list, so an earlier len() measured CHARACTERS and produced a bogus "up to 364 senses". Measured correctly: senses are the semicolon parts, capped at 9 per entry at every level, median 4-6, and 86-90% of entries are multi-sense. Polysemy is near-universal but BOUNDED, which makes it a small choice rather than a 364-way judgement call. The strategy: sense[0] is the primary sense (JMdict orders senses by priority, and for a learner the first gloss is the teachable one) and the test asserts (a) every assembled item names the sense it means, (b) the choice reproduces from the exam seed, and (c) the strategy holds ACROSS a whole level rather than on one hand-picked item. **The second sentence of the earlier draft of this AC - "distractors come from the OTHER senses of the same entry, which is a free same-entry plausible set that needs no POS matching" - WAS WRONG, and the TASK-144 baseline (doc-23) is what proved it.** See AC#8.
- [x] #8 A BARE GLOSS QUESTION MUST NOT OFFER THE TARGET ENTRY'S OTHER SENSES, and this is enforced at WRITE time rather than trusted from the picker. doc-23 judged the baseline and all three bare `word-in-context` items had MORE THAN ONE CORRECT OPTION: "Choose the meaning of 暇." offers spare time / leisure / free time, marks spare time, and marks a learner who answers "leisure" wrong. One / all day for 一日, one person / being single for 一人. The entry's other senses are not "the most plausible wrong answer" - they are other CORRECT answers, so on a bare gloss they make the item ambiguous rather than hard, and 86-90% of entries are multi-sense so this hits most of the type. THE FIX: the same-entry-senses family survives ONLY for the CONTEXTED item types, where a sentence makes one sense right and the others wrong; a bare "choose the meaning of X" has nothing to disambiguate with, so its distractors come from OTHER WORDS through the same-POS filter AC#3 already specifies. And because the defect is MECHANICALLY DETECTABLE - the corpus view has the entry's own sense list - it is a store-time invariant in the shape of the TASK-142 mask rule: an assembled bare-gloss item is rejected if any option is in the target entry's sense list. Asserted over a whole level, not on one hand-picked item, and asserted both as a picker property and as the write-time refusal.
- [x] #9 A GRAMMAR ANCHOR IS SPENT ONCE PER PAPER ACROSS ITEM TYPES, not just once per vocabulary word. AC#4 spends a word, and nothing stopped two ITEM TYPES from spending the same grammar POINT: in the doc-23 baseline the particle and reading-info items shared `grammar:masu-polite-verb`, the same sentence and the same answer, so the paper asked one question twice. The word-spend set is already per-paper; extend it to grammar ids, which is also what lets TASK-140's focus prior track a grammar anchor in its own spent-set (a grammar anchor spends no word) without special-casing. A distribution assertion over an assembled paper: no two items share a grammar anchor.
- [x] #10 A DISTRACTOR FOR A GLOSS MUST BE PLAUSIBLE, not merely non-ambiguous, and the shipped tags are not enough to get there. Found by the AC#8 fix: with the own-senses family withdrawn, the same-POS pool became visible for the first time and it is weak. Assembled verbatim: "Choose the meaning of 入口." offered entrance / yellow / salt / skillful - unambiguous, but a learner eliminates three options without reading Japanese. The same-POS filter is NOT the bug (塩 really is tagged noun in the shipped data); the bug is that the tags are coarse and single-kanji colour and flavour words carry noun tags while their glosses read as adjectives, so a tag match is a filter over a pool and never a form-class or meaning-class guarantee (doc-21 §3 says this and the pool finally shows it). Two acceptable fixes, and the choice belongs to whoever takes this: (a) tighten the filter with a secondary signal - the target gloss shape, or a curated synonym/contrast list per entry, or (b) hand-curate distractor sets for the N5 gloss set and treat the filter as the fallback for everything else. What is NOT acceptable is the current state, which is a fix that trades a correct answer being marked wrong for an item a learner cannot be tested on.
- [ ] #11 AC#10 STATUS, measured 2026-09-28 rather than inferred from the earlier WordNet figure (which this text used to carry: "2,269 of 8,505" and "35% coverage" - both superseded by the sense-group join e33d52c/2b46ac5, so they were stale here). THE NUMBER: over 40 shortened papers per level with the vocabulary section requested, every bare-gloss item that reached the store recorded the `from-own-group` sourcing case - 360 of 360 at N5 and 360 of 360 at N3, i.e. 100%. No item shipped with a same-POS-pool distractor, and the exhaustion fallback (`single-group-fallback`) never fired in the sample. WHAT THAT COST: the same papers DECLINED 179 anchors at N5 and 174 at N3. Plausibility is no longer bought with weak options; it is bought by refusing to ask. So AC#10's rule - the answer's own sense group is untouchable and every other group is a real distractor, with the picker declining an entry that has no other group - is what closed the "entrance / yellow / salt / skillful" defect, and the gate for it is `exam-sense-group-distractors-dropped` (scripts/mutation-gate.ts), which breaks BOTH withholding guards because either one alone still withholds the group. WHAT IS STILL OPEN, and it is breadth rather than tuning: 3,918 of the 8,476 shipped entries have exactly ONE sense group, so they can never produce an own-group distractor and the paper answers them only by not asking. Reaching those entries needs either a curated contrast set per entry or the agent judgement TASK-146 gates, and doc-23 §3 already says the precision call is a judgement about Japanese that an agent should not make alone. That is content work, so this AC stays unchecked: the number is honest, the remaining gap is not a filter to tune.

AC#10 DONE, and the fix was at the JOIN rather than downstream of it. Two commits: e33d52c restored the data, 2b46ac5 wired the exam.

THE ACTUAL DEFECT, and it was never a distractor problem. `fetch-vocab.ts` flattened JMdict with `for (const sense of ...) glosses.push(...englishGlosses(sense))` and joined with "; ". One JMdict sense holds several glosses that are RENDERINGS of the same meaning, so splitting `meaning` on ";" never produced senses - it produced synonyms. 黄色 is ONE sense, "yellow | amber". 入口 is ONE sense, "entrance | entry | gate | approach | mouth". Every part of each is a correct answer to "what does this mean?", so AC#8's bug was STRUCTURAL: an exam built by splitting that string cannot tell a wrong answer from a right one, and no amount of filtering downstream could fix it.

The rule is now one line. A sense GROUP is one meaning and every member is a correct answer, so the answer'"'"'s own group is untouchable and every OTHER group is a real distractor. AC#8 and AC#10 are the same rule read from two sides, and neither half needs a heuristic.

MEASURED over ten assembled N5 papers, 70 bare-gloss items: 63 (90%) now carry a REAL sense-group distractor, and 0 offer a same-group one. Before, that first number was 0 and every item read like "entrance / yellow / salt / skillful". 体 is now torso / trunk / body / build and 止まる is to cease / to come to a halt - questions about the word rather than about elimination.

COVERAGE is a property of the data now, not of a tool: 99% of entries carry `senses` (8,481 of 8,505), 3,918 have exactly ONE group and therefore offer nothing of their own, 4,563 have two or more.

WHAT THE WORDNET EXPERIMENT GOT WRONG, since it was tried first and reverted in c75cd5b. It read `meaning`'"'"'s semicolons as sense boundaries, so for the 1,196 single-sense entries it labelled same-sense renderings as "confirmed distinct" and served 黄色 as amber / yellow / younger brother / angle - AC#8'"'"'s bug, live, from the fix for AC#8. It reached 35% of multi-sense entries where the corpus itself reaches 99%, and the information had been available the whole time. The lesson worth keeping: when a data problem looks like a ranking problem, check whether the data lost a field before building a ranker.

TWO OF MY OWN INTERMITTENT FAILURES, and the second is the one that matters. I twice wrote a one-off test failure off as noise, in a commit message, before reading the line number. It was my own change: AC#3'"'"'s attested-surface set was built from `sensesOf`, which reads the 8-gloss-capped `meaning`, while the picker draws from every sense - so a distractor from sense 12 of a polysemous word was a real corpus surface the assertion could not see. The fix belongs in the helper, because `meaning` is a summary of `senses` and building the set from the summary was only ever right while the summary was all there was. An intermittent failure is the worst kind to hand-wave, and "recorded rather than claimed away" was dressing up not having looked. 195/195 on eight consecutive root runs after the fix.

ONE OBSERVATION NOT ACTED ON: 人'"'"'s primary sense is the suffix reading "-ian (e.g. Italian)", so its answer is a poor thing to teach. AC#7 assumed sense[0] is the teachable one and that is not always true. Choosing a better primary is a selection question rather than a correctness one, and it is a judgement about Japanese that doc-23 §3 already flagged as one an agent should not make alone.

THE MUTATION GATE WAS REPORTING FALSE PASTS FOR EVERY SERVER SEAM, and AC#6's seam is what exposed it. `scripts/mutation-gate.ts` ran each seam's command with `cwd: ROOT`, but `apps/server`'s env schema needs `CORS_ORIGIN` and `DATABASE_URL`, which only `apps/server/.env` supplies (bun loads `.env` from the cwd). So from the repo root the suite died in env validation, exited non-zero, and the gate scored that as "the mutation was caught" without running one assertion. Reproduced directly: `bun test apps/server/test/exam-grammar-once.test.ts` from the root exits 1 on an UNMUTATED tree.

The proof that this mattered rather than being theoretical: the AC#7 seam I was writing used `entry.senses?.[0]?.[0] ?? fullSensesOf(entry)[0]` → `fullSensesOf(entry)[0]`, which is a semantic NO-OP (measured: identical for all 8,476 corpus entries, 0 differences). It had been reported caught. A gate that cannot tell a break from a broken harness is not a gate.

Three fixes in `scripts/mutation-gate.ts`:
1. `resolveTestRun` runs a seam's command from the package root that owns its test paths (walking up to the nearest `package.json`), and passes those paths absolute. It refuses a command whose paths span two packages instead of guessing a cwd.
2. `baselineStatus` runs the command on an UNMUTATED tree first, memoised per command, and a non-zero baseline makes the verdict `untrustworthy` rather than `caught`. This is the guard that would have caught all of it on the first run.
3. `exam-gloss-reads-truncated-summary` strengthened from the no-op to what actually shipped before 35a4d09: `(entry.meaning ?? "").split(";")[0]?.trim()`, which mangles アウト to `out (of a ball` and marks that as the answer. It is now caught for the right reason.

One bug found while writing fix 1, worth remembering because it hid behind the same exit code: the `ok: true` discriminant was missing from a successful return, so `run.ok` was `undefined`, the error branch printed `! undefined`, and the harness reported -1. TypeScript would have said so; the gate is run with `bun`, which strips types without checking them.
