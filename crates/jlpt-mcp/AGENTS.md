# crates/jlpt-mcp

## Purpose

- A stdio MCP server exposing the JLPT corpora (vocabulary, grammar, conjugation, kanji, pitch-accent) to ACP agent CLIs (opencode, kilo-code, …). Spawned by the agent as a child process when the user configures `ACP_MCP_SERVERS=jlpt-vocab:stdio:<binary>`. The parent `crates/AGENTS.md` covers the workspace-level framing (Tauri sidecar + binary size + data gzipped + sync script); this sub-canonical covers the sub-subtree-specific contracts below.

## Ownership

- Project contributors.

## Local Contracts

- Exposes MCP tools over stdio JSON-RPC (`src/main.rs`, rmcp 3.x `#[tool_router]` + `#[tool_handler]`):
  - Vocab: `lookup_vocab`, `search_vocab`, `list_vocab_by_level`
  - Grammar: `lookup_grammar`, `search_grammar`, `list_grammar_by_level`, `conjugate_verb`
  - Pitch: `lookup_pitch_accent` (each result carries a tool-layer `description` field enriched by the internal `describe_pitch` helper — no separate exposed tool), `search_pitch_accent`. Entries carry an optional `source` provenance field (`"kanjium"` authority / `"wiktionary"` gap-fill) since the TASK-23.5.3 corpus merge (136,796 entries). BOTH tools also join the row to the vocabulary corpus on its exact `(word, reading)` surface, because the pitch corpus carries no English at all and a bare はし cannot tell 橋 from 箸: `gloss` is ALWAYS present (empty when the surface has no vocabulary entry, which is most non-JLPT words), `meaning`/`partOfSpeech` only on a match, mirroring how the TS engine serialized the entry's optional fields. `Corpus::vocab_by_surface` is the index built once at load in `data.rs`; `engine::vocab_for_pitch` is the lookup seam; `main.rs::pitch_row_with_gloss` attaches the fields.
  - Sentences (TASK-23.4, doc-2 §5.2): `lookup_examples(word)`, `search_examples(query, level?, limit)`, `random_example(level?)` over the Tatoeba/Tanaka corpus — each result carries a `description` field (`jp (en) — Tatoeba #id`) via `describe_sentence`. Level is a jpLen-band heuristic (`sentence_level`: N5≤30…N1∞), not a stored column; `random_example` seeds an FNV-1a pick for determinism without a `rand` dep.
  - Kanji: `lookup_kanji`, `search_kanji`, `list_kanji_by_level`, `lookup_stroke_order` (TASK-23.5.1: returns the raw KanjiVG SVG + ordered stroke paths + number labels + element decomposition; `null` when the character is not in `data/kanjivg/kanjivg.jsonl` — kyūjitai variants are absent by design)
  - Drill source (TASK-123): `drill_candidates(level, source, limit, seed)` deterministically samples vocabulary, grammar, kanji or sentence corpus rows. It returns canonical non-empty anchors plus the raw source entry only, never prompts, options or answer keys; the 40/40/20 scheduler stays in `@manobu/item-engine`.
- Tool surface + debug gate (TASK-93, TASK-123): a session sees the **17 corpus tools** above by default. The two developer-only tools (`vaporetto_split`, `vaporetto_warmup`) are unregistered unless the sidecar is spawned with `JLPT_MCP_DEBUG=1` (exact value `1`; declare it per server — `ACP_MCP_SERVERS="jlpt-vocab:stdio:<bin>|JLPT_MCP_DEBUG=1"` or `"env": { "JLPT_MCP_DEBUG": "1" }` on the `mcp-servers.json` entry, TASK-96; the grammar and the live round trip are owned by `packages/acp/AGENTS.md`. Exporting it in the agent CLI's own environment still works and reaches every sidecar it spawns, which is exactly what the per-server map exists to avoid); resolved once per process by a `OnceLock` in `main.rs::debug_tools_enabled`, which is safe because a stdio sidecar's environment is fixed at spawn). Mechanism: `JlptServer::visible_tool_router()` takes the fresh `Self::tool_router()` that `#[tool_router]` rebuilds per request and calls `rmcp`'s `ToolRouter::disable_route`, and `#[tool_handler(router = Self::visible_tool_router(), …)]` routes `list_tools` / `get_tool` / `call_tool` through it — hidden names disappear from `tools/list` and a direct `tools/call` answers `-32602 tool not found`. Keep the gate at the router: the tool fns stay compiled (the parity tests and manual debugging call them with the flag). Regression: `tests/parity.rs::debug_tools_are_gated_by_the_env_flag`. The TASK-123 public-surface addition takes the crate to 0.6.0. `Cargo.toml` is the single source of the advertised server version: `#[tool_handler]` omits `version`, so rmcp emits `env!("CARGO_PKG_VERSION")` (TASK-95, guarded by `tests/parity.rs::initialize_advertises_the_package_version`). Do not add a version literal back.
- Data file-shape variance (TASK-23.1, sub-subtree-specific): the embedded gzipped JSON files have heterogeneous shapes — `n*.json`/`grammar/n*.json` are top-level arrays, `grammar/conjugations.json`/`pitch-accent.json` use an `{ entries }` envelope, `kanji.json` nests under `kanji` in raw KANJIDIC2 shape and is transformed to the flat TS output shape in `src/data.rs::kanji_entry`, and `sentences/sentences.jsonl` (TASK-23.4) + `kanjivg/kanjivg.jsonl` (TASK-23.5.1) are JSONL — one object per line, parsed line-by-line in `data.rs` (NOT a JSON array/envelope). `all_*` vectors are built N5→N1 (the TS engine's scan order). `include_bytes!` → flate2 decompress → serde_json parse once at startup.
- Corpus size tiers (doc-2 §6 tradeoff, TASK-23.4/23.5.1/23.6 decisions): the sentence corpus gzips to **9.5 MB** and the KanjiVG stroke corpus to **4.2 MB**; all are embedded (`include_bytes!`) rather than lazily loaded from app-data — the sidecar must run fully offline from a single Tauri `externalBin` with no resource-dir guarantee. Release binary is ~19 MB. NOTE (post-TASK-23.6 review): the JMnedict names corpus (7.5 MB gz, 743k rows) was embedded then REMOVED the same day — no consumer existed (name lookups return no glosses; the Coach answers name questions better from its own knowledge) and the +38% binary contradicted the size-first rule. The data pipeline is retained: `packages/japanese/scripts/fetch-names.ts` + `data/names.jsonl` + db migration 0004 + drizzle schema; re-adding is one `build.rs` line + one parse block + the three tool fns (see git history 518cd34). Revisit only if the corpus grows substantially; a lazy-load design would need a documented resource-resolution path.
- Tokenizer (TASK-23.1, optional `vaporetto` feature): `src/tokenize.rs` wraps the `vaporetto` crate (model `.model.zst` from `apps/desktop/src-tauri/resources/vaporetto/`, overridable via `SQLITE_VAPORETTO_MODEL`). Non-ASCII `search_*` queries keep the substring-scan hit-set, then rerank by matched-token-count with an `(score desc, index asc)` tiebreak so ties preserve corpus order. ASCII queries and non-feature builds keep the legacy substring path byte-identical to the TS golden. TASK-55: `search_vocab_with_reason` result ranking — deinflected-candidate hits (reason attached) ALWAYS outrank reading-bridge hits and are merged before them under the limit cap; the reading bridge is a PREFIX match on the stored reading (the tag is the query's renyōkei stem), never `contains()` (mid-word み from みました pulled the whole 〜む verb class and displaced 見る); single-kana deinflected forms are skipped (junk dictionary forms like み → む matched an entire verb class). Regression tests: `tests/parity.rs::search_vocab_reading_bridge_ranks_target_first` (runs with `--features vaporetto` + model) + the unit gate in `src/engine.rs` tests. TASK-54: `src/deinflect.rs` rule parity with `apps/desktop/src/lib/deinflect.ts` (verb 〜なかった a-row + irregular candidates, bare-godan-potential 行ける/買える, できる→する) is asserted by the 30-form `conjugation_sweep_30_forms` test — change one side, change both. TASK-23.26 (doc-8 §3) harvests the model's two tag channels via `tokenize_with_tags() -> Vec<TaggedToken>` (`surface` + UniDic POS1-2 `pos` + katakana `reading` converted to hiragana): `search_vocab` also matches inflected queries (たべました → stem reading たべ prefix-matches 食べる's たべる) through that channel. Model fact (doc-8 probe): mixed-script katakana queries (タベる) tokenize as ONE untagged token — the bridge fires on pure-kana/kanji-stem queries; the deinflect retry for full inflection coverage is TASK-23.27.
- Boot warmup (TASK-24.1) + predictor cache (TASK-24.2): `main()` spawns a background thread calling `tokenize::warm()` so the model load overlaps agent session setup instead of landing on the first Japanese search. The JSON-RPC loop serves `initialize` immediately — the warm never blocks readiness (verified by `apps/desktop/scripts/sidecar-warmup-smoke.sh`). The `vaporetto_warmup` debug tool loads-once + reports elapsed ms (cold call reports the decode, re-call is a OnceLock hit <100 ms; `tests/parity.rs::vaporetto_warmup_reports_load_once`; the tool itself needs `JLPT_MCP_DEBUG=1`, TASK-93). Post-warm first search measures ~10 ms. Architecture note: Tauri does NOT spawn jlpt-mcp — `lib.rs` only exports `ACP_MCP_SERVERS`; the ACP agent spawns the sidecar per session/new, so a Tauri-side warm call would hit a throwaway instance. Self-warm at process start is the correct mechanism; AC#1 of TASK-24.1 is satisfied in spirit (boot-phase warm), not by a `lib.rs` invocation. TASK-24.2 cut the load itself: profiling showed `Predictor::new` (daachorse PMA build, ~1.3M ngrams) owns ~6.5 s of the old ~8 s — NOT zstd (0.1 s), so the planned memmap/streaming route was dead. Instead `load_predictor()` reads a PRE-BUILT predictor cache (`<model>.predictor.bin.zst`, zstd-3, 26 MB) written by `examples/gen-cache.rs` (wired into `packages/db/scripts/fetch-vaporetto.ts`): `serialize_to_vec`/`deserialize_from_slice_unchecked` roundtrip carries the built automaton → boot warm 8.0 s → **1.26 s**. Cache rules: regenerate in the same commit as any model or vaporetto-pin bump (deserialization is unchecked-unsafe against stale caches); a stale/corrupt cache falls back to the ~8 s model rebuild with a stderr warning; segmentation byte-identical cache vs rebuild (spot-verified 東京特許許可局で訓練を受けた機関 + full parity suite).
- Deinflection (TASK-23.27, doc-8 §4): `src/deinflect.rs` is a self-contained rule table (`deinflect(query) -> Vec<Deinflection { form, reason, required_pos }>`, rules longest-suffix-first, first-family-wins: polite negative/past/negative, past た/だ with onbin ん/っ expansion, te て/で, conditional れば/ければ, volitional general o-row+う, want-to たい/たかった disambiguated from adjective かった by stem-tail, potential/causative られる/せる + e-row). Godan potential WITHOUT れ (買える → 買う) is deliberately engine-side (`godan_e_potential`, corpus-gated — the table alone can't tell it from dictionary ichidan forms). Engines (`search_vocab_with_reason`, `lookup_vocab_with_reason`, `lookup_examples_with_reason`) fire ONLY on zero-hit miss-retry and POS-validate every candidate against corpus `partOfSpeech`; tool layer attaches a `deinflected: <reason>` field (PolitePast etc.) to retried vocab results and a description note to retried examples. Direct-hit paths are byte-identical to pre-23.27 behavior (parity golden untouched). Coverage note: u-verb polite negative past (飲みませんでした → 飲む) ✓ via the ませんでした family; suru-verb compounds (散歩する) have no explicit する-suffix rule — stems deinflect through the IRREGULAR し→する candidates.
- Build output: `cargo build --release` → `target/release/jlpt-mcp` (the parent `crates/AGENTS.md` covers the sidecar sync via `apps/desktop/scripts/sidecar-dev.sh` + Tauri `bundle.externalBin`).
- Protocol hygiene: stdout is the MCP JSON-RPC channel. Never write to stdout except via the transport — diagnostics go to stderr.

## Work Guidance

- Keep tool output byte-identical to the TS engine: `tests/parity.rs` spawns the built binary, speaks raw JSON-RPC over stdio, and diffs against `tests/golden.json` (captured from the TS engine before deletion). Regenerate the golden only when the *data contract* intentionally changes — the pitch keys were regenerated from the Rust binary at TASK-23.5.3 (Wiktionary merge widened the hit-set: はし/うどん now also return their `source: "wiktionary"` rows). The test fails fast if the child dies at startup (EOF guard) — a startup panic is a data-shape bug, not a test hang.
- A stale golden key is refreshed, never hand-edited: `cargo build --manifest-path crates/jlpt-mcp/Cargo.toml` then `bun scripts/parity-golden.ts <key> <tool> <json-args>`, copying the triple from the `battery` table in `tests/parity.rs` (that table stays the only place the triples live). It rewrites ONE key and prints before/after. Do not regenerate the golden wholesale — a snapshot that cannot fail is not a test. When Rust and the golden disagree because *Rust* is wrong, fix Rust: of the three parity failures this closed, two were a missing feature (the pitch vocab join, never ported) and only `search_vocab_english` was genuinely stale, because widening JMdict meanings put 作る ("cr**eat**e an artistic work") ahead of 食べる in the ASCII substring scan. That is also the standing caveat on English `search_vocab`: it is a naive substring match over the whole `meaning` string, so a learner typing "eat" gets weather/death/underneath hits, and the ranking is pinned by the golden rather than by anything asserting the target comes first.
- Data shape changes touch three places together: `build.rs` file list, `src/types.rs` serde structs, and the parity golden. Note the deserialization direction: `types.rs` output is camelCase (TS byte compatibility) while corpus files are snake_case, so snake_case fields need `#[serde(alias = "...")]` alongside `rename_all = "camelCase"`.
- The `vaporetto` feature is opt-in (`cargo build --features vaporetto`) precisely so the default ~5 MB sidecar contract holds when the model is absent (binary-size goal lives in `crates/AGENTS.md`).
- Pin the `vaporetto` Rust crate to an **exact patch** (`=0.6.5` in `Cargo.toml`, mirroring the SQLite extension pin). Floating on `0.6` would let `cargo update` drift the tokenizer across the 0.6.x line — re-derive the parity golden in the same commit that bumps the pin.
