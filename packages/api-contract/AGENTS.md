# packages/api-contract

## Purpose

- oRPC contract-first API surface (TASK-71): zod schemas + `oc` procedure contracts shared by `apps/server` (implements) and `apps/desktop` (consumes). The single source of truth both sides answer to; renames here are compile errors at every affected callsite.

## Ownership

- Project contributors.

## Local Contracts

- `contract` (exported from `src/index.ts`) is a plain nested object of `oc` builders. Every procedure declares `.input` + `.output` — a contract without `.output` types the client result as `unknown`.
- This package imports ONLY zod + `@orpc/contract`. No Hono, no `@manobu/db`, no server code: that is what lets the desktop webview import the contract without dragging server runtime into the bundle. fallow enforces this (`api-contract` zone is isolated).
- Errors are part of the contract (`.errors({ CODE: { data } })`) — keys are the UPPER_SNAKE ORPC error codes (`NOT_FOUND`, `TOO_MANY_REQUESTS`); handlers throw them via `errors.CODE()` and clients infer the shapes via `safe` + `isDefinedError`. Add expected failure modes here, not as undocumented thrown shapes.
- Before writing or changing contracts, load the `orpc-contract` skill (`.agents/skills/orpc-contract/`); for serving/client work use the `orpc` skill. v2 beta differs from pretrained v1 knowledge — prefer fetching https://orpc.dev/docs/<page>.md over guessing.
- Wire format (verified against oRPC 2.0.0-beta.35): `POST /rpc/<dotted.path.join('/')>` with JSON body → `{"json": <output>}` envelope.
- Versions: `@orpc/*@beta` pinned by exact version in THIS package.json, not the root catalog — betas don't belong in the catalog; bump all three packages (`@orpc/contract`, `@orpc/server`, `@orpc/client`) together.

## Work Guidance

- Lift schemas verbatim from the Hono routes they mirror (e.g. `InsertCardsSchema` in `apps/server/src/routes/cards.ts`) so legacy-route and oRPC validation can't drift while both are live. Once a schema is lifted, the route IMPORTS it back rather than keeping its own copy: `routes/cards.ts` validates `POST /cards/grade` with `GradeInputSchema` from `schemas/cards.ts`, the same schema the oRPC handler uses (TASK-166 deleted the route's private `GradeSchema`, which was the twin that had drifted). Shared numeric bounds are exports of this package too — `RETENTION_MIN`/`RETENTION_MAX`/`DEFAULT_RETENTION` are the band `GradeInputSchema` enforces and the band `apps/desktop` clamps its slider against; do not restate them in a consumer.
- One file per domain group (`cards.ts`, `jap-data.ts`, `learn.ts`), re-exported through `index.ts`; no barrel re-exports beyond that (fallow flags unused barrel exports).
- `schemas/chat-frames.ts` (TASK-80.2) is the AionUi `IResponseMessage` frame vocabulary: a zod discriminated union on `type` (start/content/thinking/plan/acp_tool_call/acp_permission/ask/finish/error/…), consumed by `chat.subscribe` (`asyncIteratorObject(ChatFrameSchema)`) over the WS link and by the client reducer in `packages/chat-session`. `chat.ts` declares every chat procedure with `.input` + `.output` + `.errors({ CONVERSATION_BUSY, NOT_FOUND })`; the `ChatFrame` type re-export is the client's frame input type. TASK-80.14 note: `chat.subscribe` no longer carries a `lastEventId` resume cursor — resume is a connect-time history read + the server's in-flight snapshot; the frame envelope itself is unchanged. TASK-101: `chat.createConversation` is DELETED (the first turn's `ensureConversation` is the only writer and the client mints its own id, so it was unreachable contract surface); `chat.getConversation`/`listConversations`/`renameConversation`/`deleteConversation` are the history surface (`listConversations` = `{ before?: {id, updatedAt}, limit }` keyset input (limit defaults 50, caps at 100), `{ conversations, nextCursor }` output, most recently ACTIVE first, `id` breaking timestamp ties so the walk is total). `MessageRowSchema` carries `type` (the frame discriminator the row was stored under) because the client's `cardsFromRows` fold rebuilds the wire frame from the row alone — a loose object without it types `row.type` as `unknown`. TASK-102 AC#4/#6: the `finish` frame gained an optional `error: { code?: "AUTH_REQUIRED"|"CONFIG_SWITCH_FAILED", message }` (a `TurnErrorSchema`) so a failed turn carries its reason to the client instead of a bare error stop-reason; `acp.ts`'s `ModelCatalogSchema` gained a REQUIRED `authRequired: boolean` — the honest signed-in/signed-out signal (only `true` when the server actually 401s on the cold model fetch), and `chat.acp.agents.models` declares `.errors({ AUTH_REQUIRED })` beside `NOT_FOUND`. TASK-126 adds the key-free `paper` frame: its generation payload carries only receipt counts, section state, mode/floor label, and optional submitted result/debrief facts, never an answer key or listening script. TASK-137 tightened the frame's result `sections[].id` to `ExamScoringSectionId` and REMOVED its `label`: a stored frame is replayed through `ChatFrameSchema.safeParse`, so a name written into it is a name that outlives the naming rule. Section `id` plus the frame's `level` and `mode` is the fact; `examScoringSectionLabelForMode` is the only reader (TASK-173.3: the `paper` fold needs the mode too, because a real frame names its sections in Japanese).
- TASK-125 extends the live chat wire with a `drill_item` frame. Its item schema is the ACP DTO's key-free shape; `resolution` and `snapshot` are separate. The WS-only `chat.startDrill` opens a bounded session, `chat.answerDrillItem` settles a pick, `chat.skipDrill` records an ungraded skip, and `chat.stopDrill` ends with the real snapshot. `chat.listConfirmations` includes `drill_item` for in-memory recovery. `DrillSnapshotSchema` carries optional honest counters (`correct`, `skipped`, `unanswered`, `nextReview`) without exposing answer keys before a pick.
- `exam.ts` is the paper/exam contract slice. `exam.request` accepts the resolved request (`level`, `mode`, optional `sections`/`budget`/`focus`/`conversationId` and `seed`; the server mints a seed when omitted); `exam.assemble` takes an exam id and leaves candidate assembly server-owned. Both return the strict build receipt with lifecycle status, real validated/total slot counts, the policy mode/floor label, and section metadata. **TASK-148 adds `contentExhausted: boolean` to that receipt**: the paper is short because this level has no UNSEEN content left for this learner, which is a different sentence to say than `shortfall > 0` from a validator rejection or a thin corpus. It is true only alongside a shortfall, so a ready paper can never claim the learner has run a level dry, and it is the field both learner-facing surfaces read (the desktop's build notice and the host tool's refusal). **TASK-173.1 adds the third `EXAM_MODES` value `"real"` (with `EXAM_MODE_LABELS` `real-paper-banded` / `real-paper-raw-only`) and `refusedSections: ExamSectionId[]` to that receipt**: a `real` paper that turns down a fabricated candidate is short for the opposite reason from an exhausted level, so the two are separate fields and only the build that refused can set this. **TASK-173.4 adds the third fact, `unfilledBlocks: ExamUnfilledPaperBlock[]`** (`{ bigQuestion, name, requestedItems, section }`, strict): the 大問 the official shape asks for that the item engine has no question kind for, which no amount of unseen content fills and no refusal caused. The three never share a field, because "you have run this level dry", "the mode turned down a candidate it could only have invented" and "this paper asks parts the app cannot ask yet" are three different sentences with three different fixes, and only the first sets `contentExhausted`. `unfilledBlocks` is empty for every mode but `real`, which is the only one with an official shape to miss. **AC#4's grouping is on the read path, not a migration**: `ExamSectionState.blocks` is `ExamPaperBlock[]` (`{ bigQuestion, instruction, itemCount, name, requestedItems }`) and `ExamComposedItem.bigQuestion` is the 大問 number or `null`. **TASK-173.2 puts the paper's own Japanese on this slice**: `ExamItem.stem` (`string.min(1).nullable()`) is the line the real paper prints for that 小問 and `ExamPaperBlock.instruction` the sentence it prints once under the 大問 heading, both null when there is no line to print. `prompt` stays exactly the English stem the daily modes ask with, because which of the two a mode shows is a presentation rule the server cannot know per learner; `speech` keeps its own documented listening exception, and a `stem` is different in kind: it is what the learner READS, and every mode has one or is meant to. The wire carries the NUMBER rather than a `PaperBlockId` union, because the number is unique inside a 科目, the 21-literal engine enum cannot cross this boundary without a second copy of the table, and a flat mode simply has none. `api-contract` still imports no server or item-engine module. `schemas/chat-frames.ts` takes `label` from `ExamModeLabelSchema` rather than re-listing the strings, because a frame that copies the enum rejects the paper it carries when a mode is added; the parity proof is `apps/server/test/exam-mode-parity.test.ts`.
- TASK-127 adds the durable running-paper surface: every `ExamSectionState` carries `paused`, `pausedMs`, `pauseCount`, and `remainingSeconds`; `exam.pause`, `exam.resume`, and `exam.abandon` are fetch procedures. `ExamState` includes `abandonedAt`, and submitted `ExamResult` includes the aggregate `pauses: { count, totalMs }`. These are the only clock/result additions; answer keys and listening scripts remain server-only.
- Exam client projections are strict: the running `ExamStateSchema` remains key-free, while submitted-only `ExamDebriefSchema` adds the per-item client item, `correctIndex`/`correctOption`, `explanation`/`explanationGenerated`, `anchorLabels` (TASK-160: the learner-facing name of each anchor in `anchors` order, EMPTY when the corpus cannot name one, and the only anchor field a surface may interpolate into a sentence — `anchors` itself is a corpus id like `vocab:N5:05d1e396…` or `grammar:dewa-arimasen-negative-polite-copula`, and stays because dispute, replay and `weakAnchors` are keyed by it), and the durable dispute flag. `exam.result`, `exam.debrief`, and the `exam.review` alias are submitted-only and declare `NOT_FOUND`, `NOT_READY`, and `CONFLICT`; `exam.dispute` is also submitted-only and returns the idempotent mark without rewriting `exams.result`. Request and lifecycle mutations declare `INVALID_REQUEST` where malformed requests are possible. The `paper` chat frame's optional `abandoned` flag marks the durable end state without inventing a result. Its `debrief.weakAnchorLabels` is the learner-facing NAME beside `weakAnchors` ids (TASK-160), and it is OPTIONAL because a stored frame is replayed through `ChatFrameSchema.safeParse` (TASK-137): a paper written before the field still parses, it just has no names to show. The contract imports no server or item-engine module.
- TASK-128 keeps the review facts in the submitted-only debrief/review response: `item` is key-free, `correctIndex`/`correctOption` are the post-submit answer data, `explanationGenerated` distinguishes agent prose, and `disputed`/`disputedAt` survive reload. The two explanation fields are independent in the schema, so a consumer cannot treat the flag as a promise of text: no composed exam item has an explanation (TASK-137), and both the review row and the drill card check the prose too. `chat.startDrill.itemId` is the exact stored-item replay seam; the server must not call the batch provider when it is present.
- TASK-131 adds `long-reading` to the exam item-type vocabulary. It is a client-safe item type with the same four-option shape, but the N3 paper engine assigns it only to `grammar-reading` and requires a passage before it can validate. The scoring section ids that include `reading` are N1/N2 (TASK-131) and, since TASK-173.13, N3 too: their `language-knowledge` band is the split column (the folded N4/N5 one folds reading in and has no separate `reading` id), so `examScoringSectionLabel({ id: "language-knowledge", level: "N3" })` returns "Language Knowledge" / 言語知識（文字・語彙・文法）, matching the official 得点区分. N1/N2 project one combined test section into three submitted-only 60-point result columns; N3 projects its three SEPARATE test sections (vocabulary / grammar-reading / listening) into the same three columns, sourcing `language-knowledge` across both vocabulary and grammar-reading.
- TASK-132 adds `integrated-reading` and `integrated-listening` to `EXAM_ITEM_TYPES`, and `ExamItemSchema` gains a required `stimuli` array of `ExamStimulusSchema` (`{ kind: "passage", text }`). The `kind` is a literal on purpose: an integrated N1 item can depend on a script AND a passage, and the script must never reach a client, so only the passage is expressible on the wire. `passage` stays as the first passage for single-stimulus consumers; the desktop renders every entry in order.
- TASK-173.5 adds `context-cloze` to `EXAM_ITEM_TYPES`: the 文脈規定 cloze the `real` 大問 walk asks. It reuses the unchanged client-safe four-option `ExamItem` shape, and its blanked word is masked in the stimulus (`context-word`, the sibling of `trailing-literal`) before it reaches the wire, so no answer crosses the boundary. The flat daily mixes weight it 0, so only `real` ever emits it and `shortened`/`exam-conditions` never show this type.
- TASK-173.6 adds `star-ordering` to `EXAM_ITEM_TYPES`: the 文の組み立て sentence-assembly item the `real` 大問 walk asks. It reuses the unchanged client-safe four-option `ExamItem` shape too: the four options are plain scrambled fragments (no ★ or blank marker is ever glued into an option string), and the marked sentence, with its ★ slot and `＿＿` blank cells, is the masked stimulus (`fragment-span`, the third verified strategy) so no answer fragment crosses the boundary. The flat daily mixes weight it 0, so only `real` ever emits it and `shortened`/`exam-conditions` never show this type.
- TASK-173.7 adds `short-reading` to `EXAM_ITEM_TYPES`: the 内容理解（短文） comprehension item the `real` 大問 walk asks. It reuses the unchanged client-safe four-option `ExamItem` shape, but it is the first real-mode type whose passage is printed UNMASKED: the learner reads the whole licensed 短文 to answer, so there is no blank to protect and no stimulus strategy applies (unlike `context-cloze`/`star-ordering`), the comprehension line rides `stem`, and the answer is the option that MATCHES the passage's meaning rather than a string lifted out of it, so nothing crosses the wire as a leak. The flat daily mixes weight it 0, so only `real` ever emits it and `shortened`/`exam-conditions` never show this type.
- TASK-173.9.7 adds `info-search` to `EXAM_ITEM_TYPES`: the 情報検索 lookup item the `real` 大問 walk asks at N5/N4/N3. Same client-safe four-option `ExamItem` shape and the same unmasked-passage reasoning as `short-reading` (the learner reads the whole licensed notice; the lookup question rides `stem`), except the answer is deliberately printed IN the notice, which is what a lookup item is, so the wire shape carries nothing new and no masking applies. The flat daily mixes weight it 0, so only `real` ever emits it and `shortened`/`exam-conditions` never show this type.
- TASK-173.9.3 adds `text-comparison` to `EXAM_ITEM_TYPES`: the 統合理解 item the `real` 大問 walk asks at N2/N1, and the first type whose SHAPE needs two documents rather than one. No new field: it rides the TASK-132 `stimuli` array, which already carries an ordered passage set, so a pair is two `{ kind: "passage", text }` entries and the desktop renders each as its own paragraph in order. `passage` stays the first-passage projection (`packages/db/src/item-store.ts:2738` writes `passage ?? firstStimulusText(...)`), so the wire never has to answer "which of the two is the passage". The Japanese comparison question rides `stem`, both documents are printed UNMASKED (nothing is blanked; the reader holds both texts and answers what they share), and the flat daily mixes weight it 0, so only `real` emits it and `shortened`/`exam-conditions` never show this type.
- Section naming has ONE declaration (TASK-137): `exam.ts` exports `EXAM_SECTION_LABELS`, `EXAM_SCORING_SECTION_LABELS`, `examSectionLabel(id)` and `examScoringSectionLabel({ id, level })`. The scoring call takes a level because the id cannot decide the name alone: `language-knowledge` is the split Language Knowledge column at N1/N2/N3 (TASK-173.13 put N3 on this side) and the folded Language Knowledge·Reading one at N4/N5, where the `reading` id never appears. Every consumer calls these (the server's receipt, the `paper` fold in `@manobu/chat-session`, the desktop result pane, the offline fallback), and `apps/server/test/exam-section-labels.test.ts` pins each blueprint's ids and official names in order, per level. Before this, five private `sectionLabel` maps each re-derived the name from the id with a partial `if` chain whose default arm swallowed the two level-dependent ids, which is how one screen came to say `Vocabulary 120/120` beside `Language Knowledge·Reading 120/120`.
- **TASK-173.3 adds the Japanese twin tables beside the English ones, not in place of them**: `EXAM_SECTION_LABELS_JA` and `EXAM_SCORING_SECTION_LABELS_JA`, each `satisfies Record<…, string>` over the same unions so a new section id fails to compile rather than falling back to a name that means something else, and each mirroring the English table's structure exactly (the scoring table spreads the section table and adds `reading`, and `language-knowledge` stays absent from both because it is the one level-dependent name). Two mode-aware choosers read them: `examSectionLabelForMode({ id, mode })` and `examScoringSectionLabelForMode({ id, level, mode })`. `real` selects the official Japanese 科目 (the names a real paper prints, off the 問題の構成 pages: doc-26 §8); every other mode (`shortened`, `exam-conditions`, this app's own formats) selects the English name, and the scoring chooser's non-`real` arm calls the unchanged `examScoringSectionLabel`, so the two languages can never disagree about which id folds reading. The English functions `examSectionLabel`/`examScoringSectionLabel` are byte-for-byte what they were: internal, non-learner contexts keep calling them directly and are unaffected by mode (AC#2). Every learner-facing surface now calls the `…ForMode` chooser with the paper's mode; `apps/server/test/exam-section-labels.test.ts` pins both languages per level and loops `EXAM_MODES` (skipping `real`) to prove a non-`real` mode still returns the English name.
- The JLPT level vocabulary has ONE declaration: `schemas/jap-data.ts` exports `JlptLevelSchema` (the zod value) and `JlptLevel` (its `z.infer`). `exam.ts` `ExamLevelSchema`/`ExamLevel` and `chat-frames.ts`'s `paper` frame alias that schema rather than re-listing the five strings, and `LevelQuerySchema` carries the `.default("N5")` so the bare enum stays strict. Adding a level is a one-line edit here; the desktop's runtime `JLPT_LEVELS` and `item-engine`'s `PAPER_LEVELS` are separate lists that cannot import this package (both zones are boundary leaves) and are pinned by tests instead. Do not add a second `z.enum(["N5", …])` anywhere in the contract: two enums over the same tuple are two independent validators, and the type union is identical either way, so the compiler cannot catch the drift.
- Naming: a zod value export ends in `Schema` and the bare name means the type. The level enum used to be `JlptLevel` for both, which forced a `biome-ignore lint/performance/noBarrelFile` justification at `index.ts` explaining that the name was overloaded. Keep the convention so the index needs no per-export carve-out.

## Verification

- `bun run -F @manobu/api-contract check-types` — the compiler IS the contract test. `implement(contract)` + `os.router` on the server fails to compile if an implementation is missing or returns a shape the contract forbids; every client call site fails to compile on a contract rename. Runtime unit tests in this package are deliberately omitted — oRPC's compile-time guarantees replace them, and behavioral evidence comes from server route tests + browser verification of consuming surfaces.
