# packages/db

## Purpose

- Drizzle ORM + libSQL data access layer for the manobu SQLite/Turso database. Single exported `db` instance plus a `createDb()` factory.

## Ownership

- Project contributors.

- Item storage (TASK-122, `doc-16` §3):
  - Migrations `0007_items_and_sessions.sql`, `0008_drill_pool_lifecycle.sql`, `0009_drill_adaptation.sql`, `0010_exam_state.sql`, `0011_exam_clock.sql`, and `0012_exam_review.sql` are imported into `src/migrate.ts`; 0007 adds `items`, `exams`, `exam_items`, `drill_sessions` and `drill_attempts`, 0008 adds the durable `drill_session_lifecycle` generation/cap row and `drill_pool_items` runway, 0009 adds durable skip state plus repeatable attempt/pool rows for adaptation, 0010 adds exam lifecycle timestamps/current section plus `exam_sections` and `exam_answers`, 0011 adds per-section `active_ms`, `paused_ms`, `pause_count`, `timer_started_at`, and `paused_at`, 0012 adds the durable `items.disputed`/`disputed_at` review mark, 0013 adds the `items.stimuli` JSON stimulus set, and 0014 adds the durable `exams.focus` JSON list, and 0015 adds `items.mask`. The DDLs are idempotent so a process exit between statements does not wedge the next boot; the current migration version is 16.
  - **TASK-173.2 `items.stem` (`0016_item_stem.sql`, text nullable)**: the Japanese line a real paper prints for one 小問, null for an item a real paper does not ask in that shape. Stored rather than re-derived at read time on purpose: the cue it comes from exists only inside the generated English `prompt` at creation, so deriving it would make an already-printed paper depend on a corpus row still resolving later. `ItemCore`/`decodeItem`/`toClientItem` carry it, `storeItem` writes `input.stem ?? null`, `validateItemInput` rejects an empty string (a stem names a printed line; there is no such thing as a zero-width one), and `itemInputComparators` compares it so re-storing an item cannot silently change what the paper prints. Adding the migration moved `PRAGMA user_version`, which is DERIVED from `MIGRATION_FILES.length`: the SQL file, its `MIGRATION_FILES` entry and its `IDEMPOTENT_MIGRATION_FILES` entry go in the same commit, and the count pins in `test/item-store.test.ts` move with them (16 to 17 here) - they are an arithmetic consequence of the list, not expectations to adjust.
  - `src/item-store.ts::createItemStore` is the only storage seam. Papers compose shared item ids through `exam_items`; deleting an exam or drill session cascades its child rows but preserves `items`, so a missed item remains reusable by exact id. The exam lifecycle methods guard `draft → ready → in_progress → submitted` plus `abandoned`; readiness requires an explicit validation attestation and checks composed section counts. `recordExamAnswer` is insert-once per item. `pauseExam` settles active milliseconds and stamps `pausedAt` once; `resumeExam` closes paused time and starts a new timer segment; `advanceExamSection` submits only the current section and starts the next pending section; `submitExam`/`autoSubmitExam` settle active sections without rewriting answers; `abandonExam` settles clocks but never creates a result. `getExamResult` is non-null only for a submitted exam, while `getExamState` and `listExamItems` remain server-side.
  - **TASK-141 speaking projection**: `ItemForClient.speech` is the text a listening item speaks, and null for every other type. `SPEAKING_ITEM_TYPES` (exported, so the exam service's resolution path decides identically) is `listening-detail` plus TASK-173.8.1's four 聴解 blocks (`listening-kadai`, `listening-point`, `listening-hatsuwa`, `listening-sokuji`) — each one's only stimulus is its script, so the client cannot answer it without the text it synthesizes. `integrated-listening` stays excluded (its script is one of several stimuli, the shape TASK-132 owns). This is a listening-only documented exception to TASK-132's "a listening script must never be projected": the audio is synthesized on the client by sherpa-onnx, the models live in the Tauri shell, the sidecar has no TTS, and the script is persisted on the item, so on-demand replay is exact and nothing is cached. `stimuli` still projects passages only (`itemStimuliForClient`), and an integrated-listening item's accompanying passage still travels as `passage`.
  - **TASK-142 mask record**: `items.mask` is the masking record as JSON, nullable, and `ItemResolution.mask` is `ItemMask | null` (the `MaskStrategy`/`ItemMask` types live in `@manobu/item-engine/types` because a masking record is a property of an item, not of the assembler). `maskRecord` normalizes an incoming mask to the PERSISTED shape - it drops the presentation-only `masked` field, which is already the item's passage, and fixes key order so a JSON comparison cannot trip - and it enforces the invariant `verified: true` is legal only with `trailing-literal`, on the way IN; `decodeItemMask` enforces it again on the way OUT, so a hand-edited cell cannot read as valid. A cell the store cannot read throws, like `stimuli`. NOT projected to `ItemForClient`: the reader is the review surface TASK-137 owns, and a contract field with no reader is the doc-21 §2 defect shape.
  - **TASK-148 served anchors**: `listServedAnchorsForLevel(level)` is the seen set the paper picker deals against, derived from `exams.level → exam_items → items.anchors` with no second ledger that could drift. Only the statuses where the learner was actually shown the paper count (`SERVED_EXAM_STATUSES`: `abandoned`, `in_progress`, `submitted`) — the pane renders a question only from the section `startExam` names, so a `draft`/`ready` paper has served NOTHING and counting drafts would let an unopened request quietly spend a level's content. Two consequences of deriving it are accepted deliberately: an abandoned paper still counts, because it did show those questions, and deleting an exam forgets its anchors, because the exam rows ARE the record. The result is `readonly string[]`.
  - **TASK-139 request round-trip**: `exams.focus` is the paper request's `focus` list as JSON, `NOT NULL DEFAULT '[]'` because `parseRequest` yields `[]` for a request that carried none, so no null/empty distinction is needed. It exists so `requestForState` in `apps/server` rebuilds the request the learner made rather than a lookalike — without it a resumed exam is a different request from the one submitted, and nothing detects the drift. `StoredExam.focus` is a `string[]` decoded through `decodeStringArray` (the same helper `drill_sessions.anchors` uses); `ExamForClient` OMITS it on purpose, because it is an assembly input with no rendering consumer, and adding it would be a declared field with no downstream reader. Two mutation-gate seams pin the chain: the service's `focus: state.focus` and the store's `JSON.stringify(input.focus ?? [])`.
  - **TASK-132 stimulus set**: `items.stimuli` holds the declared `{ kind, text }` JSON set and `passage`/`script` stay its materialized FIRST stimulus, so a multi-stimulus item still reads as a passage item to every single-stimulus consumer. `ItemResolution` and `ItemForClient` no longer share a base: the resolution carries the full set (`Stimulus[] | null`) while the client view is passages only (`itemStimuliForClient`), because a listening script must never be projected — **narrowed by TASK-141**: `toClientItem` now sets `speech` for the `SPEAKING_ITEM_TYPES` listening types, the one documented exception, because synthesis is a client concern; every other item type still projects null. A `stimuli` cell the engine cannot read is corruption and throws, like a bad `anchors`/`options` payload. The write path stores the declared set only, so a single-stimulus row is byte-identical to a pre-0013 row, and `itemMatchesInput` compares the same materialization the write produces (an input that declares only `stimuli` matches a stored row whose singular columns were filled from it).
  - `renderItem` returns the client-safe shape without `answerIndex`, `fsrsVocabId`, listening `script` or a pre-pick `explanation`; `resolveItem` is the explicit server-only key payload. `renderExam` is the client projection for composed papers and uses `selectedIndex` for a learner's saved pick, never the item key or option-source metadata. `fsrs_vocab_id` is accepted only for word-backed item types, so grammar and listening items cannot fabricate a card link. `markItemDisputed`/`isItemDisputed` own the idempotent `items.disputed` mark; the drill lifecycle drops disputed pool entries at draw time, while an explicit exact-item replay may still resolve the stored id.
  - `markDrillItemAsked`, `answerDrillItem` and `getDrillSessionState` make asked/answered/remaining recoverable after pause and database reopen. `answerDrillItem` returns `{ attempt, recorded }`, so only the first answer claimant can run the FSRS side effect; `skipDrillItem` stores `skipped=true` without counting the attempt as a miss. The historical unique `(session_id, item_id)` index is replaced by a non-unique lookup plus ordered latest-attempt selection, allowing one exact missed-item requeue per session. `drill_pool_items` stores ready/asked/dropped/superseded runway entries; `drill_session_lifecycle` stores the session type cap, generation and two-round supersession counter. `claimDrillItem` atomically changes a ready row to asked and inserts the unanswered attempt; `appendDrillPoolItems` accepts an expected generation so a late refill cannot repopulate a superseded set.
- sqlite-vaporetto (TASK-23.1, doc-2 §5.1; TASK-49 patch):
  - The shipped extension is upstream **v0.4.0 PLUS the local predictor-cache patch** — NOT the release tarball. Rebuild via `bun run scripts/build-vaporetto-ext.ts` (clones v0.4.0, applies `third_party/sqlite-vaporetto-v0.4.0-predictor-cache.diff`, builds with the model embedded, sha256-verified into `apps/desktop/src-tauri/resources/vaporetto/ext/`). Reason: upstream rebuilds the 58MB-model Predictor on every FTS5 x_create (~6.5s per vaporetto table per connection — 5 tables froze migrations >60s); the patch caches one Arc<Predictor> per process (cold ~6.5s once, then ~0ms). The guard is `test/vaporetto-migrate-perf.test.ts` (dual-mode wall-clock bounds) — if the ext is ever replaced with an unpatched build, that test fails fast.
  - `src/vaporetto.ts` resolves the extension + model paths for the app; `SQLITE_VAPORETTO_MODEL` overrides the model location. Resolution (TASK-49/50/53): `SQLITE_VAPORETTO_EXT` set → use verbatim; `=""` (empty) → EXPLICIT disable (unicode61); unset → ancestor walk from BOTH the exe dir and cwd looking for the marker `apps/desktop/src-tauri/resources/vaporetto/ext`, then a packaged `resources/vaporetto/ext` layout beside the sidecar (the destination `bundle.resources` maps the assets to; `lib.rs` sets the sidecar cwd to the resource dir). Never resolve from `import.meta.url` alone — inside a `bun build --compile` binary it is `/$bunfs/...` and the path is garbage (that exact bug silently ran unicode61 in every dev boot until 2026-09-10). The walk returns the **asset root** (`…/vaporetto`, the parent of `ext`/`model`) and `VAPORETTO_EXT_DIR` / `VAPORETTO_MODEL_DIR` hang off it — they used to return a repo root and re-append the repo path, which made the packaged branch unreachable by construction: a bundle that DID stage the assets still booted unicode61. Both layouts are pinned by `test/vaporetto-layout.test.ts` (the live root is a module-level const from the real exe dir and cwd, so the spec drives `__test__.assetRootFor` instead). Consequence when nothing resolves, stated because it is silent and learner-visible: FTS freezes at unicode61 and `apps/server/src/services/exam-mask.ts` cannot segment Japanese, so every derived candidate is unmaskable — a real paper loses 文脈規定 and 文の組み立て and reports `contentExhausted`.
  - **Tokenizer upgrade (TASK-53 follow-up, `migrate.ts::upgradeFtsTokenizerToVaporetto`)**: a db migrated while the ext was unavailable has its FTS tables frozen at unicode61 — user_version says "applied", so 0002-0004 never re-run. When the ext NOW loads but `vocab_fts` DDL says unicode61, migrations 0002-0004 are re-applied with the vaporetto tokenizer: pre-drop the six FTS tables + eleven triggers, SKIP `ALTER TABLE` statements (comment-aware line filter — they share chunks with leading comments and are already applied), gated on `vaporettoLoaded` (ext-less connections must never touch vaporetto DDL). SQL-side warm limitation (TASK-24.2 AC#4): the ~7 s cold cost of the extension's first `vaporetto_*` call lives INSIDE the third-party extension binary (hotchpotch/sqlite-vaporetto v0.4.0 — upstream-controlled load path, no streaming/mmap option at this pin); the app amortizes it via the post-migration `vaporetto_split(' ', ' ')` warm in `createContentDatabase`. The Rust-side equivalent was fixed with the pre-built predictor cache (see `crates/jlpt-mcp/AGENTS.md` — `fetch-vaporetto.ts` also writes `<model>.predictor.bin.zst` via `crates/jlpt-mcp` example `gen-cache`; regenerate it on any model or vaporetto-pin bump).
  - `src/migrate.ts` opens the native `libsql` handle, loads the extension on that connection, and applies migrations — the FTS5 tokenizer is per-connection, so extension loading and table creation/querying must happen on the same handle.
  - Migration `migrations/0002_fts5_vaporetto.sql` adds `vocabulary_fts`/`grammar_fts`/`kanji_fts` with `tokenize='vaporetto'` for Japanese columns (ASCII columns keep unicode61). Only the bare `tokenize='vaporetto'` directive works on v0.4.0 — the `tags`/`model`/`wsconst` args are `main`-branch syntax, not in the pinned release.

## Work Guidance

- FTS5 tables over Japanese text use the sqlite-vaporetto tokenizer; the extension must be loaded on the same connection that creates or queries those tables (see `src/migrate.ts`). ASCII/romaji columns keep unicode61 so English search behavior is unchanged.
- Do not upgrade the pinned sqlite-vaporetto artifact without re-verifying the `CREATE VIRTUAL TABLE … tokenize='vaporetto'` directive against the new release's grammar — released syntax lags the `main`-branch README (doc-2 §7.1).
