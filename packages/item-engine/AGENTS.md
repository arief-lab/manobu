# packages/item-engine

## Purpose

- Pure JLPT item policy shared by drill sets, generated papers and the kana checkpoint: item validation, deterministic selection and attempt-to-FSRS grade mapping.

## Ownership

- Project contributors.

## Local Contracts

- `QuestionItem`, `ItemSurface` and `ItemType` are the canonical item vocabulary. `packages/db` consumes these types rather than defining a second list. Server adapters parse untrusted batch output with Zod before calling the pure semantic validator; this package stays dependency-free.
- `validateQuestionItem` is pure. Corpus resolution, option provenance and semantic satisfaction are injected through `ItemCorpusView`; the module never reads files or a database.
- Validation returns one named rejection reason in a stable order. It never repairs an invalid item.
- `selectItems` emits the five-slot due/weak/new/due/weak cycle, applies due precedence and the caller-supplied per-type cap, and returns an explicit shortfall instead of borrowing from another bucket.
- `mapAttemptToFsrsGrade` is the only item-attempt performance-to-grade table. Response timing is classified by the caller; the package does not invent slow/fast thresholds.
- The `paper` subpath owns deterministic N5-N1 paper policy: official test/scoring blueprints, floor-aware shortened defaults, request validation, largest-remainder item-type allocation, seeded option order, paper validation and assembly, and a key-free client projection. `PAPER_MODES` is `real` / `shortened` / `exam-conditions` (TASK-173.1) and must stay identical to `EXAM_MODES` in `@manobu/api-contract`; `apps/server/test/exam-mode-parity.test.ts` pins the two sets and the label union. A casual request still resolves through `defaultPaperMode` to `shortened`. Exam persistence and lifecycle state remain outside this package.
- The paper assembler reuses `validateQuestionItem`; rejected candidates and shortfalls stay explicit, and no paper client projection carries `answerIndex`, explanations, listening scripts, FSRS links or option-source keys. `paperModeLabel` returns `<mode>-paper-raw-only` whenever the viability floor is unmet and `<mode>-paper-banded` otherwise, including an undersized `exam-conditions` or `real` request, so a raw result can never be presented as an official score. `real` takes the official section minutes like `exam-conditions` and takes its per-section item mix from the 大問 table below; what the server adds is selection honesty (it refuses fabricated candidates), which stays outside this package.
- **TASK-173.4 大問 blocks: the shape a `real` paper is assembled from**. `PAPER_BLOCKS` lists the 大問 each level prints, in exam order, numbered the way the paper numbers them (N2/N1 run one continuous sequence across the merged 言語知識・読解 科目; the other levels restart per 科目). Order, numbering and names are read from the current official レベル別 大問のねらい PDFs; `indicativeCount` is from the 2009 問題構成例 sheet, whose own footnote calls those counts 目安 and whose section times predate the 2020 and 2022 reforms. No current official document states per-block counts, so they are shape targets and must never reach a learner as the real paper's numbers (doc-26 §0 and §3). **TASK-173.12 AC#1**: `test/paper.test.ts` quotes each fillable 大問's official ねらい sentence verbatim from those PDFs and asserts every item type the block lists matches it, and guards that `conjugation` appears in no block's `itemTypes` at any level while its N5 grammar-reading weight stays > 0 (so `shortened` keeps asking it).
  - `allocatePaperBlocks` walks the table for one section, caps each 大問 at its count, and reports `requestedItems` plus `unusedBudget`, so a budget smaller than the official shape takes the 大問 from the front and leaves the rest asking for nothing rather than quietly dropping them. `allocatePaperMix` is the single source of truth for a section's item-type counts: `real` uses the block walk, every other mode the flat largest-remainder spread.
  - `PAPER_BLOCK_SHAPES` records what each 大問 may ask. Twenty-one shapes have item types today, the 読解 fifteen first: `kanji-yomi` (漢字読み), `bunmi-kitei` (文脈規定, TASK-173.5), `bun-no-bunpou-1` (TASK-173.12: `grammar-form`/`particle` only), `bun-no-bunpou-2` (文の組み立て, TASK-173.6), `bunshou-no-bunpou` (文章の文法, TASK-173.9.24), `naiyou-rikai-tanbun` (内容理解（短文）, TASK-173.7), `naiyou-rikai-chuubun` (内容理解（中文）, TASK-173.9.2), `naiyou-rikai-choubun` (内容理解（長文）, TASK-173.9.12), `shuchou-rikai-choubun` (主張理解（長文）, TASK-173.9.2 slice 2), `jouhou-kensaku` (情報検索, TASK-173.9.7), `tougou-rikai` (統合理解, TASK-173.9.3), `youhou` (用法, TASK-173.9.23), `hyouki` (表記, TASK-173.9.25), `goseikei` (語形成, TASK-173.9.26) and `iikae-ruiji` (言い換え類義, TASK-173.9.27 WORD form at N1/N2/N3 + TASK-173.9.28 SENTENCE form at N4/N5 — one 大問, two item shapes, routed per blueprint row), plus the six 聴解 shapes `kadai-rikai` (課題理解), `point-rikai` (ポイント理解), `gaiyou-rikai` (概要理解, TASK-173.9.4.1 — ONE coherent monologue, the block's own `monologue` scenario shape, shipped at N1/N2/N3), `hatsuwa-hyougen` (発話表現) and `sokuji-outou` (即時応答) (TASK-173.8.1 — one heard scenario, one printed question, four options), plus `choukai-tougou-rikai` (聴解統合理解, TASK-173.9.4.2 — ONE long dialogue heard ONCE backing TWO 小問, the `listening-choukai` type, shipped at N2 by TASK-173.9.4.2 and at N1 by TASK-173.9.4.3) — every 読解 大問 is now one of the filled twenty-one, 表記, 語形成 and BOTH forms of 言い換え類義 closed all four 語彙 shapes, and 聴解 now ships at N1/N2/N3/N4/N5; no block shape is left empty and no 聴解 大問 is owed at any level - `choukai-tougou-rikai` filled at N2 by TASK-173.9.4.2 and at N1 by TASK-173.9.4.3. The predicate asks whether a source EXISTS, not whether it is big enough, so a store smaller than the 大問's 小問数 stays an ordinary shortfall.
  - `paperBlocksForLandedItems` re-derives the grouping on the read path instead of storing it. It walks the plan and gives every 大問 its heading with the count it actually reached, so a 大問 short of its plan keeps its heading rather than losing the whole section's grouping (TASK-173.5: 文脈規定 leans on a grammar pool a level can run out of, so a real N5 vocabulary paper routinely fills it only partway). It returns null only when a landed row is not a type its own 大問 asks for, or there are more rows than the shape holds, so the desktop never prints a 大問 number the server cannot stand behind.
  - A `real` request's per-section budget is clamped to `paperSectionIndicativeCount` in `parseBudget`, so a receipt's shortfall is the size of the real gap and never counts 小問 the official paper does not have.
- **TASK-173.2 AC#1/#3: `PAPER_BLOCK_INSTRUCTIONS` is where a 大問 says what its 小問 ask**. `paperBlockInstruction({ block, level })` returns the instruction sentence the paper prints under the 大問 heading, or null for a (level, 大問) no sample PDF in this repo has been read for. Ten strings, the two blocks the engine can fill × five levels, and every one is quoted verbatim from the level's own sample paper and pinned row-by-row against its source (`test/paper.test.ts`, 10 rows naming e.g. `N5V.pdf p.2 (もんだい1)`, `N2G.pdf p.1 (問題7)`; N2G/N1G are excerpt PDFs that start mid-科目, so their 文法 sentence is read from 問題7/問題5, not from a 大問 heading). The strings live in this table rather than in the ui copy deck, because the deck holds one key per rendered label while this wording is a per-(block, level) lookup that belongs to the same shape data as `PAPER_BLOCK_SHAPES`: a learner-facing 大問 with no copy-deck key would print nothing (recorded as the AC#3 mechanism deviation on the task). N4/N5 print hiragana-spaced ことば/えらんで ください and N2/N3 kanji-dense 言葉/選びなさい, so the split is by level band and is part of the transcription, not a style choice. Guarded: no Latin letter (the papers set the options １・２・３・４, never 1234), no em dash (R-02, the same rule `packages/ui/test/copy-snapshot.test.ts` enforces for the deck), and every string names １・２・３・４から. Mutation seam `paper-block-instruction-never-resolves`.
- **TASK-173.5 `context-cloze` (文脈規定)**: a new `ItemType` the real-mode 大問 walk fills `bunmi-kitei` with. A cloze is a grammar example sentence with one word blanked (`＿＿`) and four same-part-of-speech options; the learner picks the word the sentence originally held. The blanked word is masked with the `context-word` strategy, the sibling of `trailing-literal` (TASK-142). `context-cloze` is weighted 0 in every flat section mix, so only `real` asks it, through the block walk, and it never leaks into `shortened` or `exam-conditions`.
- **TASK-173.6 `star-ordering` (文の組み立て)**: a new `ItemType` the real-mode 大問 walk fills `bun-no-bunpou-2` with. A star item is a real grammar example sentence decomposed into four contiguous fragments that rebuild it byte-for-byte; one fragment slot is marked ★ in the passage and the four fragments are offered scrambled as the options, the learner picking the one that fills ★. The marked region is masked with the `fragment-span` strategy, the third verified strategy alongside `trailing-literal` and `context-word` (TASK-142): it re-tokenizes the masked line and refuses the mask unless the fragment is gone, so an unmasked answer never ships claimed as masked. `star-ordering` is weighted 0 in every flat section mix, so only `real` asks it, through the block walk, and it never leaks into `shortened` or `exam-conditions`. It was enabled in `PAPER_BLOCK_SHAPES` only after the measurement floor passed (clean fillable sources per level: N5 77 · N4 89 · N3 127 · N2 145 · N1 150, all past the ≥5 needed for the 5-slot block). Selection honesty (an ambiguous star whose distractor also rebuilds a corpus-attested sentence is refused) is owned by the server; see `apps/server/AGENTS.md`.
- **TASK-173.7 `short-reading` (内容理解（短文）)**: a new `ItemType` the real-mode 大問 walk fills `naiyou-rikai-tanbun` with. A 短文 is a short passage printed whole and unmasked, its Japanese comprehension question carried as `stem`, and four Japanese options; unlike `context-cloze`/`star-ordering` it masks nothing, so the answer is a recorded option, not a blanked span. `STIMULUS_REQUIREMENTS` owes it one passage (`minPassages: 1`), and it is a stimulus-answered type, so the validator reads only the stem for leak evidence. `short-reading` is weighted 0 in every flat section mix (`emptyItemTypeWeights`/`emptyItemTypeCounts`), so only `real` asks it, through the block walk, and it never leaks into `shortened` or `exam-conditions`. The passage is authentic only where a store is vendored, and the stores come in two shapes: N5 ships the licensed set (`packages/japanese/data/reading/n5.json`, CC BY-SA 4.0), N3 and N4 ship AUTHORED 書き下ろし passages in their own 短文 band (`{n3,n4}.json`, TASK-173.9.18 and TASK-173.9.19, which replaced N4's blanked in-level noun of TASK-173.9.6), and N2 and N1 still blank one noun of a short 白書 paragraph (`{n2,n1}.json`). A level with no store leaves the block short, so a real paper refuses rather than reuse `LONG_READING_PASSAGE`. The sourcing and the refuse-not-fabricate decision are owned by the server; see `apps/server/AGENTS.md`.
- **TASK-173.9.7 `info-search` (情報検索)**: a new `ItemType` the real-mode 大問 walk fills `jouhou-kensaku` with. A 情報検索 item is ONE 案内 / お知らせ / じこくひょう document printed whole and unmasked like a 短文, one Japanese lookup question carried as `stem`, and four Japanese options. The official N5/N4 ねらい asks whether the learner finds the needed information in a single written-down 情報素材 (250字程度 at N5, 400字程度 at N4), so `STIMULUS_REQUIREMENTS` owes it exactly one passage (`minPassages: 1`); the multi-document shape is its own type, `text-comparison` below. The lookup answer sits IN the notice by design, so `info-search` joins `STIMULUS_ANSWER_TYPES` and the validator reads only the stem for leak evidence; a missing passage validates as `passage-missing`. `info-search` is weighted 0 in every flat section mix (`emptyItemTypeWeights`/`emptyItemTypeCounts`), so only `real` asks it, through the block walk, and it never leaks into `shortened` or `exam-conditions`. Every level whose blueprint has the 大問 now fills it, and no two levels read the same material: N5 alone ships the 12 verbatim paper-7 rows CC BY-SA 4.0 (`packages/japanese/data/reading/n5-jouhou.json`); N3 and N4 ship 8 AUTHORED 書き下ろし 素材 rows each over four written documents (`{n3,n4}-jouhou.json`, TASK-173.9.18 and TASK-173.9.19), which replaced the earlier copy of those twelve N5 notices with only the `level` stamp changed: a ねらい problem, not a licence one, because the official 大問 budgets a 書き下ろした情報素材 (600字程度 at N3, 400字程度 at N4) and a 160–245-rune N5 案内 is neither; and N2 and N1 ship six COMPOSED PDL1.0 情報素材 rows each (`{n2,n1}-jouhou.json`, TASK-173.9.13) because no licensed notice reaches that far: a 素材 the 大問's genre admits (a published fee or benefit table from a Japanese government agency) and this repo composes, cell-exact from a vendored snapshot. The band an authored 素材 must clear (`JOUHOU_AUTHORED_BAND`) sits entirely above the licensed set, so the borrow cannot return as a silent regression. A level with no file still leaves the block short and the receipt names the hole. The sourcing and the refuse-not-fabricate decision are owned by the server; see `apps/server/AGENTS.md`.

- **TASK-173.9.25 `word-spelling` (表記)**: a new `ItemType` the real-mode 大問 walk fills `hyouki` with (`paper.ts:342`), at every level that prints the 大問 (N5 大問2 / もんだい２ 8 小問, N4 大問2 6 小問, N3 問題２ 6 小問, N2 問題２ 5 小問; N1 has no 表記 大問). - **`src/hash.ts` owns the ordering primitives (TASK-135, and the follow-up)**: `hashString` (int32 `Math.imul` + an `fmix32` avalanche), `seededPermutation` (a seeded Fisher-Yates) and a module-private mulberry32. `paper.ts` and `selection.ts` both import from it and neither keeps a copy — the two files used to carry separate `hashString` definitions, and the selection one was the degenerate half. Two rules, both paid for in a bug: never build a sort key whose only difference is its FINAL character, and never prove a shuffle by asserting determinism (the identity is deterministic too; assert the distribution or the "ids differing at the end" property). `selection.ts` still has no production caller, so its new-bucket order is unproven in the app: `test/selection.test.ts` pins it directly instead.
- **The option order is a seeded permutation, not a sorted hash (TASK-135)**: `deterministicOptionOrder` hashes the item identity ONCE (`examId\0seed\0itemId`) into a mixed 32-bit seed and then runs a Fisher-Yates with `seededRandom` (mulberry32). The previous version sorted four hash keys that differed only in their LAST character, and in a djb2-style accumulator the final character is the lowest-order term, so the order came out ascending by option index for EVERY item: the "seeded shuffle" was the identity and every generated paper answered A. Two rules follow. Never build a sort key whose only difference is its final character. And never assert a shuffle by checking that it is deterministic (that holds for the identity too) — assert the distribution, because an item legitimately draws the identity 1 time in 24. `hashString` also carries an `fmix32` avalanche: without it, ids differing in one character give adjacent seeds and a per-item order degrades into a global one. `selection.ts` still has its own copy of the OLD `hashString` and the same sort shape, so the package now holds two divergent copies of one idea and the sort there is degenerate for any id set that differs only in its final character (`paper-<hex>`, `card-101`). It has no effect today for a different reason than that: `selectItems` has ZERO callers (the `./selection` subpath is exported and nothing imports it, not even another package). Treat it as a landmine for whoever wires the selector, not as a working shuffle that happens to look fine on drill-pool ids.
